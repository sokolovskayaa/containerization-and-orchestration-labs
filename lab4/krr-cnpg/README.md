# Read-only discovery of CloudNativePG for KRR

Upstream KRR does not discover CNPG Cluster pods by default (issue #538).
`discovery.patch` extends only discovery/model/history-owner mapping, not the
CPU or memory recommendation algorithms. It reads the CNPG Cluster and its
actual Pods through Kubernetes API. It never creates a synthetic workload or
changes a Cluster/Pod. Metrics are queried by KRR from Prometheus as usual.

Upstream: https://github.com/robusta-dev/krr (MIT license).
Exact source revision is recorded in upstream-commit.txt.

Prepare an isolated Python 3.12.8 environment:

```bash
bash lab4/scripts/setup-krr-cnpg.sh
```

For the recorded run, existing metrics from context kind-shop were used.
A local `kubectl --context kind-shop proxy --port 19090` provided read access
to the existing Prometheus without the unreliable port-forward stream.

```bash
/private/tmp/lab4-krr-venv/bin/python /private/tmp/lab4-krr-cnpg/krr.py simple \
  -c kind-shop -n shop \
  -p http://127.0.0.1:19090/api/v1/namespaces/monitoring/services/monitoring-kube-prometheus-prometheus:9090/proxy \
  --history_duration 1 --timeframe_duration 0.25 --cpu-min 100 \
  --logtostderr -f json > lab4/evidence/krr/cnpg-final.json
```

The 100m floor is an explicit operational policy based on failed 10m API startup/
load checks and a successful 100m check. It is NOT the default KRR percentile.
The unmodified floor run is retained in cnpg-raw.json: postgres 26m / 137Mi,
api 11m / 100Mi, worker 10m / 100Mi. The policy run recommends 100m CPU for all
three and retains measured memory recommendations. CPU limits are added equal
to requests for critical workloads to meet Guaranteed and the lab guardrails.

The global short-history warning remains in JSON and logs; it is not hidden.
All three required workloads have numeric CPU/memory recommendations, not '?'.
These measurements were used to size the same application in a new two-node
kind cluster shop-lab4, where the resulting limits were tested separately.

## Final per-workload policy runs

The 100m common-floor trial is retained as cnpg-final.json. PostgreSQL at
100m showed throttling and connection failures. Its final report is
postgres-final.json, using -r CloudNativePG --cpu-min 250. API/worker use
deployments-final.json, with -r Deployment --cpu-min 100. Both use the same
unchanged KRR simple algorithm and real Prometheus data. Final values are
generated by lab4/scripts/derive-part5-values.py; CPU limits are adapted
for Guaranteed, while memory comes directly from the KRR result.
