# Часть 5 — приоритеты и гарантии ресурсов

Критический путь приложения — создание заказа `api → postgres`. Для этих
сервисов настроены высокий приоритет, Guaranteed QoS и PodDisruptionBudget.
Фоновый batch имеет более низкий приоритет и Burstable QoS. Все настройки
внесены в Helm-чарт shop и values, без разовых kubectl-патчей подов.

## Итоговый кластер и состояние

Итоговая проверка проведена в отдельном kind-кластере **shop-lab4**:
одна control-plane и одна worker-нода, обе Ready. Control-plane разрешает
размещение учебных приложений; конфигурация хранится в kind-config.yaml.
Старый трёхнодовый shop сохранён и остановлен после сбора исходных метрик.
Его контейнеры и диски не удалены. Для нового кластера создана отдельная
учебная база, старые данные не переносились и не менялись.

Релиз **shop**, namespace **shop**, ревизия **3**, статус **deployed**.
Три API, PostgreSQL, batch и два worker — Ready. В новом кластере установлены
CNPG и Kyverno. Все пять политик лабы 3 активны и имеют Ready=True.
Проверка server-side dry-run подтвердила отклонение пода без лимитов.

## Рекомендации KRR, включая PostgreSQL

Обычный KRR не обнаруживал PostgreSQL: CNPG создаёт поды напрямую, без
Deployment/StatefulSet. Для измерения добавлено расширение **обнаружения**
CloudNativePG в исходники KRR. Оно читает реальный Cluster и реальные поды
по метке cnpg.io/cluster, затем передаёт их штатному расчёту KRR.
Алгоритмы CPU/memory не изменены. Поддельные workload или метрики не создавались.

Patch, точный upstream commit и команды воспроизведения сохранены в
[krr-cnpg](krr-cnpg/README.md). Это локальное расширение, а не заявленная
нативная поддержка CNPG в официальном бинарнике.

Метрики брались из существующего Prometheus кластера shop по тому же shop
приложению, в том числе после успешной нагрузки на путь заказа. Окно — 1 час,
шаг — 15 секунд. Итоговые ресурсы затем проверены в новом двухнодовом кластере.

| Сервис | Первоначальный бюджет CPU / память | KRR без повышенного CPU floor | KRR с принятой CPU-политикой |
|---|---|---|---|
| api | 250m / 128Mi | 11m / 100Mi | 100m / 100Mi |
| worker | 250m / 128Mi | 10m / 100Mi | 100m / 100Mi |
| postgres | 250m / 512Mi | 26m / 137Mi | 250m / 137Mi |

Отличие от сырого CPU percentile объясняется характером ограничений в лабе.
Стратегия simple предлагает CPU request, но **не задаёт CPU limit**, позволяя
кратковременно использовать больше CPU. Если просто сделать limit равным
минимальному request, исчезает этот запас на запуск и кратковременную работу.

В проверке API с 10m наблюдались медленный старт, перезапуски по liveness и
ошибки подключения к базе; CPU throttling зафиксирован в 593 из 603 периодов.
Для API/worker принят явный параметр KRR `--cpu-min 100`. Для PostgreSQL
проверка при 100m дала ошибки соединения и заметный throttling, поэтому
принят отдельный `--cpu-min 250`. Это **эксплуатационные нижние пороги**,
обоснованные проверками, а не значения 95-го перцентиля. Они не объявляются
минимально возможным или оптимальным бюджетом.

В финальных запусках KRR эти параметры заданы явно. Результаты:
[deployments-final.json](evidence/krr/deployments-final.json) и
[postgres-final.json](evidence/krr/postgres-final.json). Сырой результат
[cnpg-raw.json](evidence/krr/cnpg-raw.json) сохранён для сравнения.
У всех трёх требуемых сервисов есть числовые рекомендации CPU и памяти.

CPU limits для API/PostgreSQL установлены равными рекомендованным requests
ради Guaranteed и обязательных лимитов из лабы 3. У worker сохранён конечный
CPU limit 250m. Значение памяти PostgreSQL теперь 137Mi по KRR, а не прежние
512Mi, выбранные до измерений.

Общее предупреждение KRR о неполной истории сохранено в JSON и логах.
Порог необходимого числа точек не снижался. Это короткое учебное измерение,
которое не покрывает полный рабочий цикл; числовые рекомендации не доказывают
пригодность для произвольной будущей нагрузки.

## Приоритеты, QoS и PDB

PriorityClass **shop-shop-critical** имеет значение 100000 и
preemptionPolicy=PreemptLowerPriority. API/PostgreSQL могут получить место
за счёт менее приоритетных подов. **shop-shop-batch** имеет значение -1000
и preemptionPolicy=Never: batch не вытесняет другие поды, но сам может быть
вытеснен критическим сервисом. Имена содержат namespace и Helm release,
поскольку PriorityClass — ресурс области всего кластера.

У каждого контейнера критических подов CPU/memory requests равны limits,
фактический статус подов — Guaranteed. У batch requests ниже limits,
статус — Burstable. Guaranteed не даёт иммунитета к scheduler preemption:
приоритет и QoS решают разные задачи. При node-pressure eviction учитываются
превышение requests, приоритет и относительный расход ресурса. Поэтому
«Burstable всегда удаляется раньше любого Guaranteed» — чрезмерное упрощение.

PDB API: minAvailable=1, при трёх готовых репликах disruptionsAllowed=2.
PDB PostgreSQL: minAvailable=1, селектор выбирает primary по меткам CNPG,
disruptionsAllowed=0. Автоматические PDB оператора отключены через enablePDB,
чтобы бюджеты не пересекались.

PDB ограничивает добровольные выселения через Eviction API, например drain.
Он не предотвращает отказ ноды и node-pressure eviction; при preemption
его соблюдение не гарантировано. Единственный PostgreSQL с PDB не становится
резервированным: добровольное удаление блокируется, но запасной базы нет.

## Исправления запуска и проверка

API получил startup-пробу до 120 секунд: liveness не перезапускает контейнер,
пока он запускается. Timeout HTTP-проб увеличен до 2 секунд.

Batch первоначально падал с Java heap space: heap по умолчанию оказался
слишком мал для массива 128Mi и служебных объектов. Через values задан
JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=70.0. После изменения batch работает
с MEMORY_MB=128 и CPU_WORKERS=1 без перезапусков. Используется standalone
Java-сборка без загрузки Gradle/Kotlin; исходная Kotlin-версия сохранена.
При дальнейшем увеличении MEMORY_MB нужно отдельно учитывать heap и лимит
контейнера, чтобы не спутать Java OOM с вытеснением под давлением на ноде.

Helm --wait не гарантирует завершение обновления CNPG Cluster. Добавлен
`scripts/wait-part5.sh`: он ждёт здоровой базы, стабильной readiness и
совпадения ресурсов реального postgres-пода с желаемыми ресурсами Cluster.
Промежуточный тест во время перезапуска базы сохранён отдельно и не считается
итоговым тестом конфигурации.

Финальная проверка: **300 запросов, 300 ответов 201,
0 ошибок, p95 успешных ответов 31.25 ms**. Запросы отправлялись
из worker-пода через Service api.shop.svc.cluster.local, с темпом 5 запросов/с.
Это проверка работоспособности части 5, а не доказательство SLA под дефицитом
ресурсов из частей 7–8. Мониторинг для исходного KRR находился в старом кластере;
настройка полноценного мониторинга нового кластера для частей 8–9 — отдельная
работа, наличие одних CRD её не заменяет.

## Применение и контекст

Отдельный kubeconfig нового кластера находится вне Git:
`/Users/ahiru/.kube/shop-lab4-config`. Контекст старого кластера сохранён; текущий kubectl context переключён на kind-shop-lab4.

```bash
export KUBECONFIG=/Users/ahiru/.kube/shop-lab4-config
helm upgrade shop lab3/chart/shop -n shop -f lab4/values-part5-final.yaml --wait --timeout 5m
bash lab4/scripts/wait-part5.sh
bash lab4/scripts/show-part5.sh qos
bash lab4/scripts/show-part5.sh pdb
```

Для повторной сборки и загрузки batch: `bash lab4/scripts/finish-part5.sh`
с тем же KUBECONFIG. Чтобы включить старый кластер обратно, сохранив данные:
`docker start shop-control-plane shop-worker shop-worker2`.

Pending/preemption (часть 6), eviction и SLA под перегрузкой (части 7–8)
в этот отчёт не включены как выполненные эксперименты.
